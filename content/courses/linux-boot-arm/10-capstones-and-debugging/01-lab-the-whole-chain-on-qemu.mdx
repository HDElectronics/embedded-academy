## Boot the chain

<Prompt
  dir="~/work/m10"
  cmd='qemu-system-aarch64 -nographic -machine virt,secure=on -cpu cortex-a57 -smp 2 -m 1024 -bios flash.bin -kernel $HOME/work/build/linux-arm64/arch/arm64/boot/Image -append "console=ttyAMA0 root=/dev/vda rootwait" -drive file=rootfs.ext4,if=none,format=raw,id=hd0 -device virtio-blk-device,drive=hd0 -netdev user,id=eth0 -device virtio-net-device,netdev=eth0'
/>

The first part is the TF-A lab's command. The rest is new:

- `-kernel` and `-append` name the kernel and its command line. Because `-bios` loads firmware, QEMU does not start the kernel itself. It offers the kernel to the firmware through its `fw_cfg` interface, and writes the command line into `/chosen/bootargs` of the Device Tree it generates.[^qemu-boot]
- `-drive` and `-device virtio-blk-device` attach `rootfs.ext4` as a virtio disk, `/dev/vda` to Linux.
- `-netdev` and `-device virtio-net-device` add the network card from the Buildroot board's `readme.txt`, so Buildroot's init can bring up `eth0`.

Press a key during U-Boot's countdown to get the `=>` prompt.

## Load and start Linux by hand

Type these at the `=>` prompt.

1. `qfw load ${kernel_addr_r} ${ramdisk_addr_r}` copies the `-kernel` file to `kernel_addr_r`, which is `0x4040_0000` on this board.[^qfw][^env] U-Boot prints `loading kernel to address 40400000 size 276fa00`, and a warning that there is no initrd: you gave QEMU none. It also copies the `-append` text into the `bootargs` variable.[^qfw-src]
2. `printenv bootargs fdtcontroladdr` shows `bootargs=console=ttyAMA0 root=/dev/vda rootwait` and `fdtcontroladdr=7e64cc20`, the address of U-Boot's own Device Tree.[^envdoc]
3. `fdt addr ${fdtcontroladdr}`, then `fdt print /psci`. The node holds `method = "smc"` and the PSCI function IDs. QEMU did not write it: TF-A did, as the next section shows.
4. `booti ${kernel_addr_r} - ${fdtcontroladdr}` starts the kernel. The `-` means no initrd; the last argument is the Device Tree.[^booti]

U-Boot prints `Loading Device Tree to 000000007d622000`, then `Starting kernel ...`, and the kernel's log follows. Log in as `root`. Run `cat /proc/cmdline`: it prints the `-append` text. Then run `poweroff`.

The last line of the session is `ERROR:   QEMU System Power off: with GPIO.` That line comes from BL31, not Linux. The kernel asked the secure monitor to switch the machine off, and TF-A's QEMU port prints its power-off message at `ERROR` level before it drives the power-off GPIO.[^qemu-pm]

## The Device Tree travels through four programs

1. **QEMU** generates a dtb for `virt`. When firmware boots, it writes it at the start of RAM, `0x4000_0000`, with `bootargs` already in `/chosen`.[^virt][^qemu-boot]
2. **TF-A BL2** opens that blob in place and adds a `/psci` node, sets `enable-method = "psci"` in every CPU node, then packs it again.[^bl2] This is why the kernel can use PSCI calls to BL31.
3. **U-Boot** takes the blob at the start of RAM as its control Device Tree.[^qemu-arm] It relocates with it and records the new address in `fdtcontroladdr`.[^envdoc]
4. **`booti`** copies the tree to a fresh place, `0x7D62_2000` in this run, writes `/chosen/bootargs` from the `bootargs` variable, and starts the kernel with that address in `x0`.[^fdt-src][^arm64]

The kernel confirms each step. It prints `Machine model: linux,dummy-virt` from QEMU's tree, `psci: PSCIv1.1 detected in firmware.` from the node TF-A added, and `Kernel command line: console=ttyAMA0 root=/dev/vda rootwait` from `/chosen`. The second core comes up with `CPU1: Booted secondary processor`: the kernel starts it with a PSCI `CPU_ON` call, which BL31 handles.[^psci]

## Read the trace stage by stage

Open `logs/qemu/m10-chain-virt.log` and find each stage:

| Lines in the log                                                                 | Stage                 | Module |
| -------------------------------------------------------------------------------- | --------------------- | ------ |
| `NOTICE:  BL1: Booting BL2`, `NOTICE:  BL1: Booting BL31`                        | TF-A in secure world  | 05     |
| `Bloblist at 0 not found (err=-2)`, then the `U-Boot 2026.07` banner             | U-Boot starts as BL33 | 05, 06 |
| `DRAM:  1 GiB`, `using memory 0x7e64f000-0x7f68f000 for malloc()`                | U-Boot relocated      | 06     |
| `fdt print /psci`, `Loading Device Tree to 000000007d622000`                     | Device Tree handover  | 07     |
| `Booting Linux on physical CPU 0x0000000000`, `Linux version 6.18.55`            | Kernel entry          | 01, 08 |
| `VFS: Mounted root (ext4 filesystem) readonly`, `Run /sbin/init as init process` | Root and PID 1        | 09     |

The kernel also prints `KASLR enabled`. QEMU puts a random `kaslr-seed` in `/chosen` by default, so the kernel places itself at a random virtual address.[^virt] Debugging with GDB, later in this module, has to turn that off.

<Deeper depth="practitioner" title="What autoboot does instead">

If you let the countdown run out, `bootflow scan` boots the same kernel. The capture in `logs/qemu/m10-chain-virt-autoboot.log` shows two detours.

First, the EFI boot manager runs. It tries `Boot0000 'virtio 0'` and fails with `EFI boot manager: Cannot load any image`, because the disk has no EFI system partition. Then the `qfw` boot method loads the kernel and runs `booti ${kernel_addr_r} ${ramdisk_addr_r}:${filesize} ${fdtcontroladdr}`.[^bootmeth] With no `-initrd`, `filesize` still holds the kernel's size, so U-Boot hands over a kernel-sized block from `ramdisk_addr_r` as an initrd (`Loading Ramdisk to 7ac90000`).[^qfw-src] The kernel rejects it with `Initramfs unpacking failed: invalid magic at start of compressed archive`, frees it, and mounts `/dev/vda` as usual.

Neither line stops the boot. Reading a trace means telling these apart from the errors that do.

</Deeper>

<Deeper depth="expert" title="Why the kernel stays at 0x4040_0000">

`booti` reads the `Image` header. If bit 3 of its flags is set, the kernel may run from any 2 MiB aligned address, so `booti` leaves it where it is; otherwise it moves it to the base of RAM and prints `Moving Image from ...`.[^booti] This run prints no such line. The header also gives `image_size`, the memory the kernel needs including its BSS, which is larger than the file. The page on boot failures uses that difference.

</Deeper>
