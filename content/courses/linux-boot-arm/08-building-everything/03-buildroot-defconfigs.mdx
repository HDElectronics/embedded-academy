<div class="t-lead">
  Buildroot 2026.02.3 ships one defconfig per board. This page lists the ones for the course boards, what each builds,
  and what it leaves in `output/images/`.
</div>

Load a defconfig with `make <name>` in the Buildroot tree, then run `make`. Every fact here comes from the files under `configs/` and `board/` at tag `2026.02.3`.

## Defconfigs at 2026.02.3

| Board                   | Defconfig                     | Also at this tag                                             |
| ----------------------- | ----------------------------- | ------------------------------------------------------------ |
| Raspberry Pi 4, 64-bit  | `raspberrypi4_64_defconfig`   | `raspberrypi4_defconfig`, 32-bit                             |
| BeagleBone Black        | `beaglebone_defconfig`        | `beaglebone_qt5_defconfig`, with Qt5                         |
| STM32MP157C-DK2         | `stm32mp157c_dk2_defconfig`   | `stm32mp157a_dk1_defconfig`, for the DK1                     |
| QEMU `virt`, 64-bit Arm | `qemu_aarch64_virt_defconfig` | `qemu_aarch64_ebbr_defconfig`, `qemu_aarch64_sbsa_defconfig` |

There is no `qemu_arm_virt_defconfig` at this tag. The 32-bit Arm QEMU defconfigs are `qemu_arm_versatile_defconfig`, `qemu_arm_vexpress_defconfig`, `qemu_arm_vexpress_tz_defconfig` and `qemu_arm_ebbr_defconfig`; of these, only the readme for `qemu_arm_ebbr_defconfig` runs the `virt` machine.[^configs][^ebbr]

## What each defconfig builds

| Defconfig                     | CPU option   | Toolchain                   | Kernel                                                                      | Bootloaders                                                           |
| ----------------------------- | ------------ | --------------------------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `raspberrypi4_64_defconfig`   | `cortex_a72` | external, Bootlin, glibc    | Raspberry Pi fork (`raspberrypi/linux`, pinned commit), `bcm2711` defconfig | none: Raspberry Pi firmware package, Pi 4 variant                     |
| `beaglebone_defconfig`        | `cortex_a8`  | external, Bootlin, glibc    | `6.18.1`, `omap2plus` defconfig                                             | U-Boot `2026.01`, `am335x_evm`, SPL named `MLO`                       |
| `stm32mp157c_dk2_defconfig`   | `cortex_a7`  | external, Bootlin, glibc    | `6.12.63`, configuration file in `board/`                                   | TF-A 2.10 LTS with SP_min, FIP; U-Boot `2026.01`, `stm32mp15_trusted` |
| `qemu_aarch64_virt_defconfig` | not set      | internal, built from source | `6.18.7`, configuration file in `board/`                                    | none: QEMU loads the kernel                                           |

All four build an ext4 root filesystem. `qemu_aarch64_virt_defconfig` also builds QEMU itself for your host.[^configs]

The DK2 defconfig asks for the latest TF-A 2.10 LTS rather than a tag. At 2026.02.3, Buildroot resolves that choice to `lts-v2.10.5`.[^atf]

<Callout level="warning">
  These versions are Buildroot's, not the course's. The course pins Linux `v6.18.55`, U-Boot `v2026.07`, TF-A
  `lts-v2.14.10` and OP-TEE `4.10.0`. The DK2 defconfig builds no OP-TEE: it uses TF-A's SP_min as BL32. It also builds
  U-Boot with `stm32mp15_trusted`, where module 06 uses `stm32mp15_defconfig`.[^configs]
</Callout>

## Images in `output/images/`

Each board's `readme.txt` lists what a build leaves behind. Buildroot's ext4 option writes `rootfs.ext2` and links `rootfs.ext4` to it, so either name appears.[^ext2]

### `raspberrypi4_64_defconfig`

The readme covers every Raspberry Pi model; these are the entries it marks for the Pi 4:[^rpi]

- `bcm2711-rpi-4-b.dtb`, and the other BCM2711 board files the defconfig names
- `Image`: the kernel
- `rpi-firmware/`: `start4.elf`, `fixup4.dat`, `config.txt`, `cmdline.txt` and `overlays/`
- `boot.vfat`: the boot partition image
- `rootfs.ext4`
- `sdcard.img`: the card image

`sdcard.img` has an MBR table with two partitions: `boot`, type `0xC`, marked bootable, 32 MB, holding `boot.vfat`; and `rootfs`, type `0x83`.[^rpigenimage]

### `beaglebone_defconfig`

The readme lists:[^bbb]

- `am335x-boneblack.dtb` and the other AM335x board files
- `MLO` and `u-boot.img`: SPL and U-Boot
- `zImage` and `uEnv.txt`
- `boot.vfat`
- `rootfs.ext2` and `rootfs.tar`
- `sdcard.img`

The board's post-build script also writes `extlinux/extlinux.conf`, which the readme does not list. `sdcard.img` has an MBR table: partition `u-boot`, type `0xC`, marked bootable, 16 MB, with `MLO`, `u-boot.img`, `zImage`, `uEnv.txt`, the `dtb` files and `extlinux`; and `rootfs`, type `0x83`, 512 MB.[^bbbgenimage]

### `stm32mp157c_dk2_defconfig`

The readme names only `sdcard.img`.[^stm] The defconfig asks TF-A for `fip.bin` and its `.stm32` images, and the post-image script derives the BL2 file name, `tf-a-stm32mp157c-dk2.stm32`, from the Device Tree name.[^stmpost] `sdcard.img` has a GPT table:[^stmpost]

| Partition | Content                        |
| --------- | ------------------------------ |
| `fsbl1`   | `tf-a-stm32mp157c-dk2.stm32`   |
| `fsbl2`   | `tf-a-stm32mp157c-dk2.stm32`   |
| `fip`     | `fip.bin`, 2 MB                |
| `rootfs`  | `rootfs.ext4`, marked bootable |

The kernel and Device Tree are not in a partition of their own. The defconfig installs them into `/boot` of the root filesystem, and its overlay adds `/boot/extlinux/extlinux.conf`.[^configs]

### `qemu_aarch64_virt_defconfig`

The readme's QEMU command uses `output/images/Image` and `output/images/rootfs.ext4`.[^qemu] The QEMU post-image script also writes `start-qemu.sh` to `output/images/`, built from that same command.[^qemupost]
