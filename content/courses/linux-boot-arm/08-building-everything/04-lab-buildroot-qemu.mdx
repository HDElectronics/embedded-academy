  In this lab you build a complete 64-bit Arm Linux system with one Buildroot defconfig, then boot it in QEMU. No board
  is needed: the target is QEMU's `virt` machine.
</div>

## Before you start

You need the lab container running, as the `labs/README.md` file of the repository describes, and the course sources fetched. If you have not fetched them yet, run this inside the container:

<Prompt cmd="sh ~/course/fetch-sources.sh" />

It clones Buildroot at tag `2026.02.3` into `~/work/src/buildroot`.

Plan for a long build. This defconfig builds its own cross toolchain from source, because it selects none; the Buildroot manual puts the toolchain alone at about 15 to 20 minutes.[^faq] It also builds a kernel, a root filesystem and QEMU itself for your host.[^defconfig] The build downloads every source it needs, so keep the network up.[^quick] The manual gives no figure for disk space; check that the disk behind `~/work` has room before you start.

## Load the defconfig

Go to the Buildroot tree:

<Prompt cmd="cd ~/work/src/buildroot" />

Load the board configuration:

<Prompt dir="~/work/src/buildroot" cmd="make qemu_aarch64_virt_defconfig" />

This writes a full `.config` from the short defconfig. Find the kernel version in it:

<Prompt dir="~/work/src/buildroot" cmd="grep BR2_LINUX_KERNEL_CUSTOM_VERSION_VALUE .config" />

The value is the version the defconfig pins, 6.18.7.[^defconfig] Buildroot chose it; it is not the course's `v6.18.55`.

## Build the system

Start the build:

<Prompt dir="~/work/src/buildroot" cmd="make" />

Leave it running. You don't need `-j`: Buildroot does not build packages in parallel at the top level by default.[^quick] When `make` returns to the prompt without an error, list the results:

<Prompt dir="~/work/src/buildroot" cmd="ls output/images" />

Look for three files:

- `Image`: the arm64 kernel;
- `rootfs.ext4`: the root filesystem;
- `start-qemu.sh`: a launcher that the board's post-image script wrote.[^post]

## Boot it in QEMU

Run the command from the board's `readme.txt`, unchanged, from the Buildroot tree:[^readme]

<Prompt
  dir="~/work/src/buildroot"
  cmd='qemu-system-aarch64 -M virt -cpu cortex-a53 -nographic -smp 1 -kernel output/images/Image -append "rootwait root=/dev/vda console=ttyAMA0" -netdev user,id=eth0 -device virtio-net-device,netdev=eth0 -drive file=output/images/rootfs.ext4,if=none,format=raw,id=hd0 -device virtio-blk-device,drive=hd0'
/>

This runs the container's own QEMU. The readme says the login prompt appears in the terminal that started QEMU.[^readme] Log in as `root`: Buildroot sets no root password unless you configure one.[^passwd]

When you are done, leave QEMU with `Ctrl+a` then `x`.[^mux]

## QEMU skips every stage before the kernel

Compare this boot with the chains in earlier modules. Here there is no boot ROM, no TF-A and no U-Boot:

- `-kernel` hands `Image` straight to QEMU, which starts it with the Linux boot protocol.
- QEMU generates the Device Tree for `virt` itself and passes its address in `x0`.[^virt]
- `root=/dev/vda` names the virtio disk that `-drive` and `-device virtio-blk-device` attach, holding `rootfs.ext4`.[^readme]

The kernel's own start is the part of the chain this lab does exercise: module 09 follows it to PID 1.

<Deeper depth="practitioner" title="Boot with the generated launcher">
`output/images/start-qemu.sh` runs the readme command with paths relative to `output/images/`. By default it puts Buildroot's own QEMU, built in `output/host/bin`, first in `PATH`. Pass `--use-system-qemu` to use the container's QEMU instead, or `--serial-only` to force serial-only output.[^post]

<Prompt dir="~/work/src/buildroot" cmd="output/images/start-qemu.sh --use-system-qemu" />

</Deeper>
