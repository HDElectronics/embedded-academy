<div class="t-lead">
  Once U-Boot has relocated and set up its devices, it has one job left: start an operating system. What it starts, and
  from where, is not hard-coded. It comes from environment variables, and above all from one of them, `bootcmd`.
</div>

## The environment holds U-Boot's settings

The environment is a list of `name=value` variables. You read it with `printenv`, change it with `setenv` and store it with `saveenv`. These are aliases of `env print`, `env set` and `env save`.[^env]

Until you save, you work on a copy in memory. A reset brings back the stored environment, or the default one if nothing was stored.[^env]

Each board ships a default environment. Newer boards write it as a text file in the board directory, with a `.env` extension. Older boards build it from C defines such as `CFG_EXTRA_ENV_SETTINGS`.[^env] This is the file for the QEMU `virt` board, which you use in this module's lab. It keeps its upstream license header, GPL-2.0-or-later:

{/* REUSE-IgnoreStart */}

<CodeBlock path="board/emulation/qemu-arm/qemu-arm.env" project="U-Boot" simplified>

```text
/* SPDX-License-Identifier: GPL-2.0+ */

/* environment for qemu-arm and qemu-arm64 */

stdin=serial,usbkbd
stdout=serial,vidconsole
stderr=serial,vidconsole
fdt_addr=0x40000000
scriptaddr=0x40200000
pxefile_addr_r=0x40300000
kernel_addr_r=0x40400000
ramdisk_addr_r=0x44000000
boot_targets=qfw usb scsi virtio nvme dhcp
```

</CodeBlock>

{/* REUSE-IgnoreEnd */}

Names ending in `_addr_r` are RAM addresses where boot commands load images: `kernel_addr_r` for the kernel, `fdt_addr_r` for the Device Tree, `ramdisk_addr_r` for the initial RAM disk. They are a naming convention, not something U-Boot's code requires, and some boards use other names.[^env]

## bootcmd runs when the countdown ends

After start-up, U-Boot counts down for `bootdelay` seconds. If you press a key, you get the shell. If not, it runs the commands in `bootcmd`.[^env] If `bootcmd` returns because nothing booted, U-Boot falls back to the shell.[^main] Setting `bootdelay` to `-1` turns autoboot off.[^env]

`bootcmd` is an ordinary variable, so you can read and change it like any other. On the boards in this course, its default comes from the Kconfig option `CONFIG_BOOTCOMMAND`.[^kconfig]

## Standard boot finds the operating system for you

Older boards found the kernel with long boot scripts kept in the environment. Standard boot replaces them with three concepts built into U-Boot:[^bootstd]

- A **bootdev** is a device that can hold an operating system: an SD card, a USB disk, the network.
- A **bootmeth** is a way to look for one on a bootdev. The `extlinux` bootmeth looks for a file, the `script` bootmeth for another.
- A **bootflow** is what a bootmeth found: a description of how to boot.

U-Boot tries each bootdev, each bootmeth on it, and each bootflow found, until one boots.[^bootstd] One command does all of it: `bootflow scan -lb` scans, lists what it finds (`-l`) and boots the first valid bootflow (`-b`).[^bootflow]

The variable `boot_targets` sets which bootdevs are tried and in what order. In the QEMU file, that is `qfw` first and the network (`dhcp`) last.[^bootstd] Through `qfw`, U-Boot can boot a kernel that you hand to QEMU with its `-kernel` option.[^qfw]

## Two files describe the boot

**`extlinux.conf`.** The `extlinux` bootmeth looks for `extlinux/extlinux.conf` at the root of a partition or under `/boot`.[^extlinux] The file lists one or more labels. Each label names a `kernel`, the kernel command line (`append`), the Device Tree (`fdt`, or `fdtdir` for a directory) and optionally an `initrd`.[^pxe] Distributions write this file; U-Boot only reads it and does what it says.[^bootstd]

**`boot.scr`.** The `script` bootmeth looks for `boot.scr.uimg`, then `boot.scr`, in the same places. U-Boot loads the file into memory and runs the commands in it.[^script] The commands are wrapped as a FIT or a legacy U-Boot image, which you build with the `mkimage` tool. The `source` command runs such a script by hand.[^source] A script gives you full control, at the price of writing the load and boot commands yourself.

<Deeper depth="practitioner" title="What each board's bootcmd runs at v2026.07">

Not every board in this course uses standard boot by default.

- **Raspberry Pi 4**: `rpi_4_defconfig` and `rpi_arm64_defconfig` enable `CONFIG_BOOTSTD_DEFAULTS` and set no `CONFIG_BOOTCOMMAND`, so `bootcmd` gets the Kconfig default, a `bootflow scan` command.[^kconfig] [^defconfigs]
- **BeagleBone Black**: `am335x_evm_defconfig` enables `CONFIG_DISTRO_DEFAULTS` and sets `bootcmd` to run board scripts, then `distro_bootcmd`.[^defconfigs]
- **STM32MP157 DK2**: `stm32mp15_defconfig` also enables `CONFIG_DISTRO_DEFAULTS` and runs `bootcmd_stm32mp`. That script picks `boot_targets` from the device the board booted from, then runs `distro_bootcmd`.[^stm32]

`distro_bootcmd` is the older, script-based distro boot. It walks `boot_targets` and, on each partition, looks for `extlinux/extlinux.conf` and then `boot.scr.uimg` or `boot.scr` under `/` and `/boot/`.[^distro] Kconfig marks it deprecated and points new boards to standard boot.[^kconfig]

</Deeper>
