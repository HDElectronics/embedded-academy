## Before you start

Open the lab container and fetch the sources, as in this module's lab. Then go to the U-Boot tree.

<Prompt cmd="cd ~/work/src/u-boot" />

Each build here uses its own output folder with `O=`, so one source tree serves all boards. `CROSS_COMPILE` names the cross compiler on the `make` command line.[^gcc] The lab container has two: `aarch64-linux-gnu-` for 64-bit Arm and `arm-linux-gnueabihf-` for 32-bit Arm.

<Deeper depth="practitioner" title="Why every build uses O=">

Once a source tree holds an in-tree configuration, the U-Boot `Makefile` refuses a build with `O=` and asks you to run `make mrproper` first.[^makefile] Build every board out of tree from the start and you never meet that error. `O=` also keeps the `.config` of each board in its own folder.[^gcc]

</Deeper>

## Raspberry Pi 4

The U-Boot documentation lists two 64-bit defconfigs for the Raspberry Pi 4B:[^rpi]

- `rpi_4_defconfig` targets the Raspberry Pi 4B only.
- `rpi_arm64_defconfig` covers the Raspberry Pi 3B, 3B+, 4B, 400, CM 3, CM 3+, CM 4 and Zero 2 W. It uses the Device Tree the firmware provides instead of an embedded one, so the same binary boots several boards.

The documentation does not prefer one. This course uses `rpi_arm64_defconfig`, because in the course's boot chain the firmware prepares the Device Tree. The list at `v2026.07` does not name the Raspberry Pi 5.

Configure, then build:

<Prompt
  dir="~/work/src/u-boot"
  cmd="make O=$HOME/work/build/rpi_arm64 CROSS_COMPILE=aarch64-linux-gnu- rpi_arm64_defconfig"
/>

<Prompt dir="~/work/src/u-boot" cmd="make O=$HOME/work/build/rpi_arm64 CROSS_COMPILE=aarch64-linux-gnu- -j$(nproc)" />

**Files the board needs.** `u-boot.bin` from the build folder. Copy it to the boot partition, next to the Raspberry Pi firmware files. In `config.txt`, `kernel=u-boot.bin` makes the firmware load it in place of the default `kernel8.img`, and `arm_64bit=1` starts it in 64-bit mode.[^config]

## BeagleBone Black

The `am335x_evm` configuration builds one binary for the AM335x GP EVM, the AM335x EVM SK and the BeagleBone family. U-Boot reads the board EEPROM at run time to tell them apart.[^am335x] The AM335x has a 32-bit Cortex-A8, so use the 32-bit cross compiler.

<Prompt
  dir="~/work/src/u-boot"
  cmd="make O=$HOME/work/build/am335x_evm CROSS_COMPILE=arm-linux-gnueabihf- am335x_evm_defconfig"
/>

<Prompt
  dir="~/work/src/u-boot"
  cmd="make O=$HOME/work/build/am335x_evm CROSS_COMPILE=arm-linux-gnueabihf- -j$(nproc)"
/>

**Files the board needs.** Two files from the build folder:

- `MLO`: U-Boot SPL, prepared for the AM335x boot ROM.[^omap]
- `u-boot.img`: U-Boot itself. SPL loads it by this name, set in the defconfig as `CONFIG_SPL_FS_LOAD_PAYLOAD_NAME`.[^defconfigs]

## STM32MP157 DK2

The STM32MP1 documentation recommends the trusted boot chain: TF-A BL2 first, OP-TEE as secure monitor, then U-Boot. For TF-A with a FIP, it names `stm32mp15_defconfig`.[^stm32] The STM32MP157 has 32-bit Cortex-A7 cores, so use the 32-bit cross compiler.

<Prompt
  dir="~/work/src/u-boot"
  cmd="make O=$HOME/work/build/stm32mp15 CROSS_COMPILE=arm-linux-gnueabihf- stm32mp15_defconfig"
/>

The defconfig defaults to the device tree of the ev1 board. Pick the DK2 with `DEVICE_TREE`. With OP-TEE as secure monitor, ST recommends the `-scmi` variant of each board's device tree.[^stm32]

<Prompt
  dir="~/work/src/u-boot"
  cmd="make O=$HOME/work/build/stm32mp15 CROSS_COMPILE=arm-linux-gnueabihf- DEVICE_TREE=st/stm32mp157c-dk2-scmi -j$(nproc) all"
/>

<Callout level="warning">

The STM32MP1 documentation writes the name without the `st/` prefix, as in `DEVICE_TREE=stm32mp157c-ev1-scmi`. At `v2026.07` this board takes its device trees from `dts/upstream/src/arm/st/`, and the defconfig's own default is `st/stm32mp157c-ev1`. The build looks for `dts/upstream/src/arm/` followed by the `DEVICE_TREE` value, so this page keeps the `st/` prefix.[^dtsmake] [^control] A build in the lab container confirmed it: without the prefix, `make` stops with `Device Tree Source (dts/upstream/src/arm/stm32mp157c-dk2-scmi.dtb) is not correctly specified.`[^dtlog]

</Callout>

**Files the board needs.** `u-boot-nodtb.bin` and `u-boot.dtb`.[^stm32] U-Boot does not boot on its own here: TF-A packs the two files into its FIP, `fip.bin`, as `BL33` and `BL33_CFG`. Module 05 covers TF-A. To swap U-Boot in an existing FIP, the U-Boot documentation uses TF-A's `fiptool` with `--nt-fw u-boot-nodtb.bin --hw-config u-boot.dtb`.[^stm32]

<Deeper depth="practitioner" title="The other STM32MP15 boot chains">

The documentation lists two more defconfigs. `stm32mp15_trusted_defconfig` is for TF-A without FIP support and produces `u-boot.stm32`. `stm32mp15_basic_defconfig` replaces TF-A with U-Boot SPL; ST does not support or promote that chain for products.[^stm32]

</Deeper>
