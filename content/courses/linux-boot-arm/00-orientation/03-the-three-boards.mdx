## One 64-bit board, two 32-bit boards

The Raspberry Pi 4 runs Armv8-A cores, so you meet 64-bit Arm and exception levels on it. The BeagleBone Black and the STM32MP157 DK2 run Armv7-A cores: 32-bit Arm, with processor modes. Each section lists the same facts in the same order: SoC and cores, architecture, boot media and lab approach.

## Raspberry Pi 4

- **SoC and cores.** Broadcom BCM2711, with four Cortex-A72 cores[^rpi-soc].
- **Architecture.** Armv8-A. The Cortex-A72 implements all four exception levels, EL0 to EL3, and can run each of them in AArch64 or AArch32[^a72].
- **Boot media.** The second-stage bootloader is stored in an SPI EEPROM on the board, not on the SD card[^rpi-flow]. It tries the boot modes listed in its `BOOT_ORDER` setting: SD card, USB mass storage and network are among them. With `BOOT_ORDER` empty, it tries the SD card, then USB mass storage, then starts again[^rpi-boot].
- **Lab approach.** QEMU has a `raspi4b` machine with four Cortex-A72 cores and 2 GiB of RAM[^qemu-raspi]. It loads a kernel, or a firmware image such as U-Boot, straight into memory and starts the Arm cores[^qemu-raspi-c]. It does not run the boot ROM, the EEPROM bootloader or the VideoCore firmware. Labs emulate the Raspberry Pi 4 from the first Arm instruction onwards, and simulate the stages before it with the illustrative logs.

## BeagleBone Black

- **SoC and core.** TI Sitara AM3358 on revision B and later boards[^bbb-soc], with one Cortex-A8 core at up to 1 GHz[^ti].
- **Architecture.** Armv7-A, 32-bit. The Cortex-A8 implements the Security Extensions[^a8], but not the Virtualization Extensions, so it has no Hyp mode.
- **Boot media.** The board boots from the 4 GB eMMC by default. If the eMMC holds no bootable image, it tries the microSD card, then the serial port, then USB. Holding the boot switch down while you apply power, with a bootable microSD card inserted, makes it boot from the card[^bbb-boot].
- **Lab approach.** QEMU 10.0 has no AM335x machine[^qemu-boards]. Steps that are generic Armv7-A run on QEMU's `virt` machine. Steps that depend on the AM335x, such as the ROM code and U-Boot SPL in internal SRAM, are simulated: you prepare the files and read the illustrative logs.

## STM32MP157 DK2

- **SoC and cores.** ST STM32MP157C, with two Cortex-A7 cores and a Cortex-M4 coprocessor. The `C` variant adds secure boot and hardware cryptography, with the Cortex-A7 at 650 MHz[^st-soc].
- **Architecture.** Armv7-A, 32-bit. The Cortex-A7 implements the Security Extensions, the Virtualization Extensions and the Large Physical Address Extension[^a7].
- **Boot media.** Switch `SW1` sets two boot pins, `BOOT0` and `BOOT2`. With both at 1 the board boots from the microSD card. With both at 0 it enters recovery, a boot over UART or USB used with STM32CubeProgrammer[^st-boot].
- **Lab approach.** QEMU 10.0 has no STM32MP1 machine[^qemu-boards]. Its `virt` machine offers a `cortex-a7` CPU[^qemu-virt], so generic Armv7-A steps run on the same CPU type as the board. Steps that depend on the STM32MP157, such as the ROM code, the first-stage loader and DDR setup, are simulated with the illustrative logs.

## Why the course still uses three boards

Emulation teaches the parts every Arm board shares: exception levels, the hand-over registers, U-Boot, the Device Tree and the kernel's start. The real boards teach what differs: who runs first, where the first loader runs, and how DRAM comes up. Every lesson says which kind of step you are reading.
