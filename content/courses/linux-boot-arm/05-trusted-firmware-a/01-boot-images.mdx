## BL means boot loader, and the number is the order

TF-A's image names start with BL, for BootLoader. The TF-A documentation calls the name a historical anomaly: several of these images are firmware, not loaders, but the name stuck.[^terms] The digits give the order. BL1 runs first, BL2 second, and the three BL3x images form the third stage.

On a 64-bit (AArch64) system, the cold boot runs in five steps, in this order:[^cold-boot]

| Image | TF-A calls it         | What it does                                                                 | Where it runs                          |
| ----- | --------------------- | ---------------------------------------------------------------------------- | -------------------------------------- |
| BL1   | AP Trusted ROM        | Starts at the reset vector, sets up the CPU, loads BL2.                      | EL3, usually from trusted ROM          |
| BL2   | Trusted Boot Firmware | Sets up the platform, loads every third-stage image, hands over to BL31.     | Secure EL1                             |
| BL31  | EL3 Runtime Software  | Stays resident. Handles every Secure Monitor Call (SMC) and switches worlds. | EL3                                    |
| BL32  | Secure-EL1 Payload    | Optional. Usually a Trusted OS such as OP-TEE.                               | Secure EL1                             |
| BL33  | Non-trusted Firmware  | The normal-world boot loader, for example U-Boot or UEFI. It boots the OS.   | Normal world, EL2 if present, else EL1 |

The levels in the last column come from the firmware design: BL1 starts at EL3, passes control to BL2 at Secure EL1, and BL31 enters BL33 "at the highest available Exception Level (EL2 if available, otherwise EL1)".[^cold-boot][^bl33]

## BL1 and BL2 load, BL31 stays

The first two images are loaders. BL1 is meant to live in ROM, so it typically cannot be modified. It does the minimum: CPU setup, a console, and loading BL2 from platform storage.[^cold-boot] BL2 does the heavier platform work, then loads BL31, the optional BL32 and BL33 into memory. When it is done, BL2 does not jump to BL33 itself. It hands the list of loaded images to the EL3 runtime, which starts them.[^cold-boot]

BL31 is different: it never exits. After it starts BL33, it keeps its exception vectors installed. Normal-world software reaches it with the `SMC` instruction, for example to turn a CPU on or off through the Power State Coordination Interface (PSCI).[^cold-boot] This is why TF-A also calls BL31 the "EL3 monitor firmware": its main purpose is to handle transitions between the normal and secure world.[^terms]

BL32 needs a partner inside BL31. TF-A calls it a Secure Payload Dispatcher (SPD). The dispatcher initializes BL32 before BL33 runs, and routes requests between the two worlds. With no BL32, BL31 passes control straight to BL33.[^cold-boot]

The hand-off relay replays this chain from a real boot on QEMU `virt`, which has no BL32. Step through it and watch BL2 call back into BL1 before BL31 starts, then BL31 leave EL3 for U-Boot. Each stage shows the entry point and the `SPSR` value it hands over.

## On 32-bit Arm, BL32 is the monitor

The STM32MP157 has Cortex-A7 cores. Its TF-A port is an Armv7-A platform, built for AArch32 with dedicated code.[^mp1] On AArch32 the chain has four steps, not five:[^cold-boot]

1. BL1, AP Trusted ROM
2. BL2, Trusted Boot Firmware
3. BL32, **EL3 Runtime Software**
4. BL33, Non-trusted Firmware

There is no BL31. The job of the secure monitor moves into BL32. The build option `AARCH32_SP` names it. TF-A ships a minimal one, SP_MIN, to show how its PSCI library fits into AArch32 runtime software. Other AArch32 runtime software can add more services, such as a Trusted OS.[^initial-build] When OP-TEE is the BL32 on a 32-bit platform, it takes this role: it is the Trusted OS and the EL3 runtime at once.[^mp1]

## The STM32MP157 skips BL1

On the STM32MP157, the chip's own ROM code plays the part of BL1. It loads only one TF-A image: BL2, wrapped in an STM32 header so the ROM can load it. BL2 then reads everything else from a single package called the FIP: OP-TEE as BL32, U-Boot as BL33, and their device trees.[^mpus] The TF-A documentation gives the sequence as ROM code, then BL2, then OP-TEE, then U-Boot.[^mpus]

Step through the STM32MP157 on the boot chain and watch the TF-A BL2 stage load OP-TEE and U-Boot.

<BootChain boards={['stm32mp157']} label="secure-chain" pane={2} />

Because there is no BL1 to call back into, BL2 must start as if it were the reset code. The ST platform files build it with `RESET_TO_BL2` set to `1`.[^st-common] The firmware design describes this mode: BL2 then runs at EL3 and jumps to the next image directly.[^bl2-el3]

For OP-TEE, TF-A's STM32MP1 page is explicit: OP-TEE is the default BL32 for ST platforms, and SP_MIN works but is "not the recommended BL32".[^mp1] On the STM32MP15, BL33 is loaded at `0xC010_0000`, 1 MiB into DDR.[^mp1-def]

On the privilege ladder, follow the STM32MP157 from the secure world to the normal world. The handover from OP-TEE to U-Boot is where the world changes.

## The other two boards use less of TF-A

TF-A's Raspberry Pi 4 port is a BL31-only port. The GPU firmware still runs first. If it finds a file named `armstub8.bin`, or an `armstub=` entry in `config.txt`, it loads that file to the start of DRAM and runs it in AArch64 EL3. TF-A's `bl31.bin` is used as that stub, and it drops into EL2 to run the "kernel" the firmware loaded.[^rpi4] The same page warns that this port is not secure: all of its memory is DRAM that the normal world can also reach.[^rpi4]

The BeagleBone Black's AM335x does not appear in TF-A's list of platform ports at this version, so its chain has no TF-A stage.[^ports]

<Deeper depth="practitioner" title="How BL2 reaches BL31 on AArch64">

With TF-A's BL1 in the chain, BL2 runs at Secure EL1 and cannot enter EL3 by itself. It raises an SMC back to BL1, giving it the BL31 entry point. BL1 turns off the MMU, flushes the caches and jumps to BL31 at EL3.[^cold-boot]

BL2 passes the list of next images to the EL3 runtime in the first argument register: `X0` for BL31 on AArch64, `R0` for BL32 on AArch32.[^cold-boot] When BL2 runs at EL3, as on the STM32MP157, the SMC round trip disappears and BL2 jumps to the next image itself.[^bl2-el3]

</Deeper>

<Deeper depth="expert" title="EL3 on a 32-bit core">

The Armv7-A architecture names its privilege levels PL0 to PL2 rather than EL0 to EL3,[^armv7] but TF-A's documents use EL3 language for AArch32 too: they speak of "AArch32 EL3 Runtime Software". Its cold boot entry requires all interrupt sources masked (`PSTATE.AIF = 0x7`) and little-endian data (`SCTLR.EE = 0`), with `R0` carrying information about the BL3x images from BL2.[^aarch32-entry]

</Deeper>
